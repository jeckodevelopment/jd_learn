# JD Learn development

- User preference: work through GitHub for every development increment. Publish the branch, open/update a pull request and inspect its actual GitHub Actions results; do not leave an increment only as a local patch.

- Use `docs/specifications/Specifica_funzionale_LMS_Joomla_1.0.md` (content version1.5), the technical design and the security/provider specifications as the scope baseline. Keep requirements and implementation status separate.
- Product name: JD Learn. Installed IDs remain com_jlms, pkg_jlms, lib_jlms and plugin group jlmsvideo. No client-specific branding and no competitor references.
- Joomla6 MVC, DI, native accounts, categories, assets/ACL, languages, forms, session/CSRF, WAM and other core features where applicable. Do not modify Joomla core or duplicate authentication/access levels.
- Subscription sales and Joomla group assignment are outside scope. Enrolment never grants groups. Recheck current access before each protected operation, including retries.
- Work in reviewable increments. Unimplemented publication, playback and student actions must fail closed. Never claim a schema/interface is a completed feature.
- Base distribution must include all four provider plugins: youtube, vimeo, cloudflarestream, html5. Plugins register a descriptor and lazy factory; the component owns authorisation, progress, completion and grading.
- No secrets, personal data, private media, answer keys or generated site configuration in git. Test credentials are limited to disposable CI fixtures. Keep runtime fixtures under ignored `.runtime/`.
- Bind SQL values, allowlist fields and sort columns, validate parent relations, escape output contextually, use core CSRF and ACL. Keep published teaching history immutable and database transitions short/atomic.
- Run `python3 tools/build.py`, `python3 tools/check.py`, relevant PHP tests and lint for code changes. Use the existing GitHub CI when the local environment lacks PHP/database; inspect actual job results. Never weaken a test just to hide a product defect.
- Database and Joomla smoke tests must run only with the explicit disposable-site opt-in. Do not execute them on a customer site.
- Update implementation status, requirement mapping, changelog and CSS/override documentation when changing the corresponding behaviour. Test release install/upgrade and current Joomla patch before production distribution.

- Documentation ownership: IMPLEMENTATION_STATUS.md is the current feature snapshot; NEXT_STEPS.md owns ordered remaining work; ROADMAP_TO_STABLE.md defines phase scope; M01_ACCEPTANCE.md separates missing implementation from pending validation. Put release-by-release notes only in CHANGELOG.md/IMPLEMENTATION_HISTORY.md, not appended to current summaries or guides. Replace superseded statements, update current evidence, and keep requirement descriptions/IDs/acceptance separate from implementation status.

- Operational efficiency: open PRs as drafts while preparing changes. Draft commits and documentation-only PRs run lightweight policy/build/structure checks; expensive integrations run only for a runtime candidate marked ready for review. Ordinary candidates use PHP8.3/MySQL8.4 and PHP8.4/MariaDB10.6 plus Chromium. Run the full four-pair compatibility matrix through workflow_dispatch(matrix=full) before milestones/releases or when changes affect PHP/database compatibility. No automatic repeat on main merge. Before adding implementation commits to an already-ready PR, return it to draft, batch changes, then mark ready again. Recheck the tested code and base against the actual merge candidate: runtime, tests, build, workflow or relevant base changes invalidate prior results; never merge unverified runtime or describe skipped checks as passed. See docs/CI_POLICY.md.

- Persistent user priorities: complete usable course management and operational YouTube, Vimeo and Cloudflare Stream publication/playback first. Treat base provider defects as immediate course-blocking work, distinct from later advanced M04 extensions. Update repository status, ordered next steps and relevant guides/evidence in every increment. Before the first candidate push, synchronise any affected guides under component/administrator/docs with their repository source so the installable package is current.

- Backend UX requirement: plan an intuitive landing page and a native JD Learn administrative sidebar menu with permission-scoped links to operational features. Track in M01/M10 and docs/ADMIN_UX_PLAN.md; course management and essential providers remain first. The native submenu and direct course-list entry are implemented in0.40; do not mark the remaining redesign or full role/browser acceptance complete.

- Video UX priority (R-06): maintain automatic duration acquisition in authoring for YouTube/Vimeo/Cloudflare Stream, retain file-derived local MP4 duration, and handle bounded metadata/player differences coherently in completion. Do not require routine exact manual duration/confirmation. Follow docs/VIDEO_DURATION_PLAN.md, preserve published history and current access, and distinguish implemented authoring from pending live provider/browser acceptance.

## Maintainer delivery conventions

- Every pull request that adds or changes user-visible/runtime behavior must include a clearly titled `## Collaudo manuale Joomla` section in its description. Give the maintainer concrete steps to perform on a test Joomla installation, the role/account or course setup needed, and the expected result for each new or corrected behavior. Do not leave this as “please test.” For a documentation-only or otherwise non-functional PR, include the same heading and state that no Joomla behavior changed and no site test is applicable.
- After every merged PR, report the overall JD Learn development progress as a percentage toward the agreed first stable version, using `docs/RELEASE_SCOPE.md` and `docs/RELEASE_SCOPE_MATRIX.md` as the boundary. Recompute consistently after each merge, exclude phase-two work, and briefly state the basis and what remains. Keep implementation progress distinct from manual acceptance; a passing CI alone does not mean the stable release is accepted. Use an explicit progress inventory/weighting if the existing status records do not support a defensible percentage; do not present false precision.
- After every merge, provide a clickable link to the installable package matching the merged runtime code. Prefer the verified GitHub Actions package artifact for that exact commit; check that its inner Joomla package version and checksum match the candidate, and say if the artifact is a wrapper ZIP that must be extracted once. For documentation-only PRs, link the latest verified installable package and identify the runtime commit it contains. If no usable artifact exists, produce and verify one before reporting completion. Mention artifact expiry when it applies.
